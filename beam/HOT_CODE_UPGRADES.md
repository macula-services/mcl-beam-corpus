# BEAM: Hot Code Upgrades

*Load a new module version into a running node, transition processes to it, keep serving. The release system's answer to "no downtime for deploys".*

---

## The mechanism

A BEAM node can run two versions of a module simultaneously: the
**old** version continues serving existing processes, the **new** one
serves processes that call it after the upgrade. Code change is
ordinary runtime behaviour, not a special event.

The machinery around it is the release system:

| Piece | Role |
|-------|------|
| **`.appup`** | Per-application upgrade instructions: which modules to load, add, delete; which processes to suspend and resume (`{load_module, m}`, `{update, m, soft}` ...) |
| **`relup`** | The release-level upgrade script, generated by `systools:make_relup/3,4` from the old and new releases |
| **`release_handler`** | Unpacks, installs, and rolls back releases on a live node |
| **`code_change/3`** | The callback a `gen_server` implements to migrate its state from the old to the new version |

---

## The flow

```
1. release_handler:unpack_release("mysystem2")
2. release_handler:install_release("SECOND")   # node switches, processes transition
3. release_handler:make_permanent("SECOND")    # survives a restart
```

After `install_release`, the new release is **current** but the old one
is still **permanent**: a node restart boots the permanent release.
`make_permanent/1` is the commit — until it runs, the upgrade is a
trial that a restart rolls back. This current/permanent split is the
rollback story: never lose the way back to the last good release.

If the upgrade touches the emulator, kernel, stdlib or sasl, the
release_handler restarts the node (with `heart` when configured);
application-only upgrades transition in place.

---

## What a process must do

A `gen_server` implementing `code_change/3` receives its old state and
the upgrade version, and returns the new state. For `{update, m,
{advanced, Extra}}` upgrades, it receives `Extra`. Processes that need
no state migration just return `{:ok, NewState}`.

The discipline: **never migrate state lazily**. If the new version's
callbacks assume a new state shape, every process that was not
migrated crashes or misbehaves. `code_change` is the single point where
old state becomes new state — put the migration there.

---

## Why fleets care

- **No-downtime deploys.** Code upgrades are the BEAM's answer to
  rolling restarts: the node keeps serving while modules swap.
- **Rollback by restart.** The permanent release is the fallback; a bad
  upgrade is undone by booting the node.
- **It is not free.** Every `code_change` is code that must be written,
  tested, and maintained forever. A fleet that upgrades by releasing
  new containers may never need the in-place machinery at all.

## Rules of thumb

- Use in-place hot upgrades where downtime is the cost that matters
  and the ops team runs BEAM natively.
- If deploys are containers or VMs, prefer the release system's
  `make_permanent` discipline anyway: current vs permanent is good
  hygiene for any versioned boot.
- Test upgrades both ways: forward (`code_change` to the new version)
  and backward (down-downgrade to the previous one).
