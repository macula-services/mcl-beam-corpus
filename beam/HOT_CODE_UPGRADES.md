# BEAM: Hot Code Upgrades

*Replace code in a running node without stopping it. The runtime makes module swapping cheap; OTP's release handling turns it into an upgrade you can install, commit and roll back.*

---

## The runtime primitive

The code server keeps at most **two versions** of each module: *current*
and *old*. Loading a new version makes the previous current version
old. Processes executing old code keep running it; a **fully qualified
call** (`Module:function(...)`) always enters the current version, which
is how a process moves over. Loading a third version purges the old one,
and any process still running in it is killed. Everything else in this
note is machinery for doing that swap in an orderly way across a whole
system.

---

## The release machinery (SASL)

| Artifact / module | What it does |
|-------------------|--------------|
| `.appup` file (per application) | Describes how to go from one application version to another, and back: `{load_module, M}` for stateless modules, `{update, M, {advanced, Extra}}` to suspend processes using `M` and run their `code_change`, `add_module`, `delete_module`, `restart_application`, `apply` |
| `relup` file (per release) | The ordered, low-level upgrade script for the whole release, generated by `systools:make_relup/3,4` from the old and new `.rel`, `.app` and `.appup` files |
| `release_handler` | Unpacks, installs, commits and removes releases on the live node |
| `code_change/3` | The `gen_server`/`gen_statem`/`gen_event` callback that converts a process's state to the new version's shape; it receives `Extra` from the `advanced` instruction |

## Installing an upgrade

1. `release_handler:unpack_release(PackageName)` extracts the package and returns `{ok, Vsn}`.
2. `release_handler:install_release(Vsn)` runs the relup. The new version is now *current*, but the old one is still *permanent*: a reboot at this point brings the old release back.
3. `release_handler:make_permanent(Vsn)` commits: the new version is what the node boots from now on.

The gap between steps 2 and 3 is the safety net: run the new code,
observe it, and only then commit. Changes to ERTS or to Kernel, STDLIB
or SASL cannot be swapped in place; the relup then starts with
`restart_new_emulator` and the node reboots into the new runtime.

---

## Trade-offs

- **Every upgrade is code to write and test,** in both directions:
  appups name downgrade instructions too, and `code_change` receives
  `{down, Vsn}` when going back.
- **State migration happens once, in `code_change`.** New callbacks that
  assume a new state shape will crash on processes that were never
  converted.
- **Most deployments do not need it.** Elixir's `mix release` explicitly
  does not support hot upgrades out of the box, and fleets that ship
  containers replace nodes instead. Hot upgrades earn their cost where
  a node's in-memory state or open connections are expensive to lose.
- **The current/permanent idea is worth copying anyway:** boot the new
  version, verify it, then commit; keep the last good version as the
  default until then. Nerves firmware slots work the same way
  ([NERVES](NERVES.md)).
